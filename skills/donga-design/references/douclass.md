# 구조, 보안, 접근성, 제출 규칙

동아출판 프론트엔드 제작 가이드(dongaguide.netlify.app)에서 디자인을 뺀 **내용 규칙만** 옮겨 정리했다. 그 가이드의 색, 글꼴, 화면 꾸밈은 따르지 않는다. 겉모양은 늘 이 스킬(당토 디자인 규격 + 동아 CI 색)을 따른다.

이 규칙은 두클래스(douclass)에 올리는 자료를 기준으로 하지만, 동아 디자인으로 만드는 모든 화면에 기본으로 적용한다. 지켜도 손해가 없고, 나중에 두클래스에 올릴 때 다시 고칠 일이 없기 때문이다. 사용자가 "독립 웹앱", "React로", "서버 있는" 등 다른 실행 방식을 분명히 말하면 4번(실행 방식)만 그에 맞게 풀고, 보안과 접근성은 그대로 둔다.

공식 로고와 저작권 문구, 공공 API 예외, 보안 검사 규칙, 용량과 성능 기준, 최종 지원 환경은 **동아출판 담당자가 확정한다.** 이 문서와 점검 스크립트를 통과해도 담당자 검사기(https://htmlcheck.dongapublishing.com/) 통과가 보장되지는 않는다.

## 1. 파일 구조

```
제출폴더/            ← 압축을 풀면 바로 index.html이 보여야 한다 (바깥 폴더를 한 겹 더 만들지 않는다)
├── index.html       ← 화면, 스타일, 동작, 퀴즈 엔진, 문항 데이터를 모두 이 한 파일에
└── assets/          ← 이미지, 소리, 글꼴만 (images/ 등 다른 이름도 된다)
    ├── fonts/       ← Pretendard woff2 + OFL-Pretendard.txt
    └── images/
```

- CSS와 JS를 따로 파일로 나누지 않는다. `tokens.css` 내용도 `<style>` 안에 붙인다.
- 자료는 `./assets/...`처럼 `./` 상대 경로로 연결한다. 하위 경로에서 열어도, 폴더를 옮겨도 보여야 한다.
- 쓰지 않는 폴더와 파일을 넣지 않는다. 비밀번호, API 키, 개인정보, `node_modules`, `.git`, 임시 파일은 제출하지 않는다.
- JSON 자료도 `fetch`로 불러오지 않고 `index.html` 안에 JS 값으로 넣는다(직접 실행과 검사기에서 문제가 된다).

## 2. 래퍼와 CSS

- 화면, 스타일, 스크립트는 래퍼 `<div class="dc-content">` 안에서만 동작한다.
- 선택자는 `.dc-content .클래스` 형태만 쓴다. `body`, `button` 같은 태그 선택자, `:root`, `*` 같은 전역 선택자를 쓰지 않는다. (`.dc-content` 자신과 `.dc-content *`는 래퍼 안이라 괜찮다.)
- `!important`를 쓰지 않는다. 우선순위는 클래스를 겹쳐 올린다.
- `position: fixed` 대신 래퍼 안의 `position: absolute`(시트, 토스트)나 `sticky`(하단 버튼)를 쓴다. 래퍼는 `position: relative`다.
- `z-index`는 100 이하. 토큰 `--z-sticky` 10, `--z-sheet` 50, `--z-toast` 60을 쓴다.
- `@import`, 외부 글꼴 주소, 외부 그림 주소를 쓰지 않는다.
- `<!doctype html>`이 파일 맨 첫 줄이 되게 한다. 편집 도구가 그 앞에 주석(저작권 머리말 등)을 넣었으면 제출 전에 `<html>` 안이나 `<head>` 안으로 옮긴다. 검사기와 오래된 브라우저에서 문제가 될 수 있다.
- `<body>`에는 여백을 없애는 `style="margin:0"` 하나만 둔다(태그 선택자를 쓰지 않으려고). 검사기에서 걸리면 지운다.

## 3. 스크립트

**쓰지 않는 것**
- HTML 문자열 넣기: `innerHTML`, `outerHTML`, `document.write`, `insertAdjacentHTML`, `DOMParser`, `iframe srcdoc`
- 이벤트 속성: `onclick="..."` 같은 `on` 속성, `setAttribute('onclick', ...)`
- 위험한 실행: `eval`, `new Function`, 문자열을 넘기는 `setTimeout`
- 통신: `fetch`, `XMLHttpRequest`, `WebSocket`, `Worker`, 동적 `import()`
- 바깥 접근: 부모 페이지(`parent`, `top`), `postMessage`, `cookie`, `window.open`, 페이지 이동(`location`)
- 링크 주소: `javascript:`, `data:`, `blob:`
- 외부 `<script src>`, `<link>`, `iframe`, `object`, `embed`, 자동 이동

**쓰는 것**
- 글자는 `textContent`, 요소는 `createElement`(SVG는 `createElementNS`), 이벤트는 `addEventListener`.
- DOM 찾기는 래퍼 요소 안에서: `const root = document.getElementById('app'); root.querySelector(...)`.
- 가이드가 제공하는 `frameH` 도우미가 있으면 써도 된다.
- 시뮬레이션 객체 라이브러리 코드는 고치지 않고 옵션과 콜백만 바꾼다.

## 4. 실행 방식

- CSS와 JS까지 담은 `index.html` 하나로 핵심 활동이 돌아가야 한다. Node 서버, DB, 학생 로그인에 기대지 않는다.
- 외부 CDN, 외부 글꼴, 외부 통신 없이 만드는 것이 기본이다. 공공기관 API는 회사가 발급하고 관리하는 것만 예외가 될 수 있고, 예외는 담당자가 정한다. 그 전에는 쓰지 않고 자료를 파일 안에 넣는다.
- 로그인, 서버 DB, 온라인 순위, 실시간 공동 편집은 기본 범위 밖이다.
- 카메라, 마이크는 https 또는 localhost에서만 동작하고 권한 허용이 필요하다.
- 지원 환경: 최신 Windows, macOS, iPadOS/iOS, Android 브라우저. 태블릿, 휴대폰의 오프라인 실행은 실제로 확인한 방식만 "지원"이라고 안내한다.
- 두클래스 뷰어는 A 방식(위아래에 뷰어 머리, 꼬리가 붙음)과 B 방식(전체 창) 중 하나를 등록할 때 고른다. A 방식이면 콘텐츠 높이가 줄어드니 첫 화면 핵심이 위쪽에 오게 한다.

## 5. 저장과 개인정보

- 기본은 저장하지 않는다. 저장이 막혀도 활동은 이어져야 한다.
- 학생 개인정보(이름, 번호, 연락처, 얼굴 등)는 모으지도 저장하지도 않는다.
- 개인정보가 아닌 값을 저장할 때도 목적, 고유 키(자료 이름이 든 키), 실패 처리(try/catch), 초기화 방법을 코드 주석과 사용 안내에 적는다.
- 라이트, 다크 고르기도 기본은 저장하지 않고 지금 화면에서만 바꾼다.
- 이미지, PDF로 바로 저장하는 버튼은 두지 않는다(`data:`, `blob:` 주소가 필요하다). 인쇄 창의 "PDF로 저장"을 안내한다.
- 두클래스 플랫폼에 있는 제목, 공유, 수업 도구 버튼을 콘텐츠 안에 다시 만들지 않는다.

## 6. 접근성

| 항목 | 기준 |
|---|---|
| 누르는 영역 | 최소 44×44px, 교실 화면은 48px 이상(`--touch-class`) |
| 키보드 | 모든 조작을 Tab, Enter, Space, 방향키로. 초점이 보여야 한다(`:focus-visible`) |
| 끌기 | 끌기 동작에는 누르기와 키보드 대안을 반드시 둔다 |
| 상태 | 눌림은 `aria-pressed`, 고름은 `aria-checked`. 색만으로 상태를 나누지 않는다(아이콘, 문구 함께) |
| 팝업 | Esc로 닫고, 닫으면 연 버튼으로 초점을 돌린다 |
| 확대 | 200% 확대에서 내용과 조작이 유지된다. viewport에서 확대를 막지 않는다(`user-scalable=no` 금지) |
| 대비 | 글자 4.5:1, 조작 경계 3:1 이상 |
| 대체 | 이미지에는 `alt`, 그래프에는 같은 자료의 표 대안(`<details>` 안 표 등) |
| 입력 칸 | 16px 이상(휴대폰에서 저절로 확대되지 않게) |
| 글자 크기 | 개인 기기 본문 18~20px 권장, 최소 16px. 교실 화면의 핵심 설명은 24~28px부터 확인 |

이 표의 기준이 당토 디자인 값보다 엄격한 곳(터치 44px, 입력 칸 16px, 학생 본문 크기)은 이 표를 따른다. 그래서 학생 화면의 글자는 16px 아래로 내리지 않고(보조 글, 그래프 눈금 제외), 오래 읽는 설명 글은 `--fs-body-lg`(18px)를 쓴다. 촘촘 모드도 버튼 높이를 44px 아래로 내리지 않는다.

## 7. 권리와 문구

- 공식 로고와 저작권 문구는 제공받은 것만 쓴다. 임의로 만들지 않는다.
- 이용 허락을 확인하지 않은 자료(그림, 지도, 소리, 글꼴)를 넣지 않는다. 출처와 이용 조건은 `sources.csv`에 적는다.
- "교육용이니 자유 이용" 같은 문구를 임의로 넣지 않는다.

## 8. 제출 문서

빌더에서 초안을 내려받아 채운다: `usage.md`(사용법), `quiz.md`(문항), `sources.csv`(출처와 권리), `review.md`(검수 기록), `README.txt`, 설정 JSON, AI 제작 안내서(.md).

## 9. 제출 전 점검 (가이드 15항목 요약)

- [ ] **내용:** 대상, 단원, 목표, 성취기준이 검수 자료와 맞는가. 개념, 수치, 정답, 해설을 확인했는가. 모형의 한계를 적었는가. 교실 뒤에서 글자가 읽히는가
- [ ] **안내:** 사용법, 교사 발문, 출처, 지원 환경 안내가 있는가
- [ ] **조작:** 마우스, 터치, 키보드로 모두 되는가. 처음으로 되돌리기가 있는가. 빈 입력, 오답, 연속 누르기에서 오류가 없는가
- [ ] **화면:** PC, 태블릿, 휴대폰과 200% 확대에서 잘리지 않는가
- [ ] **실행:** 새 폴더에 압축을 풀어 `index.html`을 직접 열었을 때, 인터넷을 끈 상태에서, 하위 경로에서 열었을 때 모두 되는가. `index.html`만 새 폴더에 복사해 열어도 이미지를 뺀 모든 조작, 퀴즈, 팝업이 되는가
- [ ] **권리, 정리:** 외부 의존, 개인정보, 이용 권리, 제출 폴더와 버전을 점검했는가
- [ ] **퀴즈:** 유형별 정답, 허용 답안, 오답 문구를 확인했는가. 키보드만으로 풀 수 있는가. 빈 입력과 다시 풀기가 되는가
- [ ] **검수 기록:** 다른 교사 1명이 시연했는가. 담당자 피드백과 확인하지 못한 항목을 `review.md`에 적었는가
- [ ] **검사기:** 두클래스 HTML 콘텐츠 검사기를 통과했는가
